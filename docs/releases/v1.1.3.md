# v1.1.3

## Summary

v1.1.3 makes the restoration pipeline crash-safe and stops it from leaving
temporary files behind.

Before this release, a job scattered its scratch state across three locations:
the generated `<stem>_temp_script.vpy` and the in-progress `<output>_part.<ext>`
were written next to the source video, and the FFMS2 index was written into the
system temp folder under `auto-vhs-deinterlancer/ffms2/`. The part file and the
index were never removed on a failed or interrupted run, and the "resume"
guarantee amounted to "skip the file if a finished output already exists" — a
power cut at 90% of a three-hour tape lost the entire encode.

Every temporary and cache artifact now lives in exactly one place, a per-video
workspace folder `<file name>.autovhs-tmp/` beside the source. Video is encoded in
fixed-length segments inside that folder, so an interrupted run resumes from the
last completed segment instead of starting over. The workspace is deleted as
soon as the final output is in place, so a successful run leaves nothing but the
output file.

## Highlights

- **Per-video temp workspace** (new `modules/runtime/workspace.py`):

  - All scratch state for one input lives in `<file name>.autovhs-tmp/` next to
    the source (the full name, extension included, so `tape.mpg` and
    `tape.mp4` in one folder never share a workspace): `restore.vpy` (generated script), `index/` (source indexes),
    `segments/` (completed and in-progress segments), `segments.txt` (FFmpeg
    concat list), `state.json` (resume fingerprint) and the muxed
    `<output>_part.<ext>`.
  - The folder is created at the start of a job, interrupted `*.part.*` files
    are deleted at every start, and the whole folder is removed once the final
    output has been renamed into place — or immediately when a valid output
    already exists. It is kept only on failure, so the next run can resume.
  - `save_state()` writes `state.json` through a `.json.part` temp file and an
    atomic `replace()`, so a power cut cannot leave a half-written state file.
  - `VideoWorkspace` is a frozen dataclass built by `build_workspace()`; every
    path a job can write is resolved in one place, which is what makes the
    "nothing outside the workspace" invariant checkable.

- **Resumable segmented encoding** (`modules/runtime/pipeline.py`):

  - New `resume_segment_minutes` setting in `config.yaml` (default `5`, `0`
    disables segmentation). It is validated at load time in
    `modules/core/config.py` and must be a number `>= 0`.
  - Each segment runs `vspipe --start N --end M | ffmpeg` as a **video-only**
    encode (`-an`) into `segments/seg_NNNN.part.<ext>`, which is renamed to
    `seg_NNNN.<ext>` only after both processes exit cleanly. A segment is
    therefore either absent or complete; a torn file is never mistaken for a
    finished one.
  - On a rerun, each planned segment that already exists and reports a positive
    duration via `ffprobe` is skipped with a `[RESUME]` log line.
  - `state.json` records the source identity (resolved path, size, nanosecond
    mtime and a SHA-256 over sixteen 1 MiB samples spread across the file, so
    a replacement that kept the size and timestamp, such as a copy made with
    preserved times, is still told apart without reading a multi-hour capture
    in full) on its own, checked *before* the script is generated or probed: a
    source replaced under the same name discards the workspace indexes and
    segments, so a stale FFMS2 / L-SMASH / BestSource index built from the
    previous file can never feed the metadata probe. It also stores a SHA-256
    fingerprint over that identity plus every setting that changes segment
    content: encoder, deinterlace mode, field order, TV standard, QTGMC
    settings, the segment length, the resolved FFmpeg video-encoder arguments
    and the QTGMC OpenCL device settings. The resolved encoder arguments matter
    because segments are concatenated with stream copy, so an `av1_nvenc`
    segment must never be reused next to a `libsvtav1` one. If any of them
    changed, the existing segments are discarded instead of being silently mixed
    with new ones. Segment removal failures propagate: a segment that survives
    a failed delete would otherwise be reused under the *new* fingerprint on the
    next run, so the job fails instead and the old fingerprint stays on disk.
  - When the frame count cannot be probed, the plan falls back to a single
    open-ended segment, which reproduces the previous single-pass behaviour.

- **Separate mux stage**:

  - Once all segments exist, FFmpeg joins them with the concat demuxer using
    stream copy (`-c:v copy`, no re-encode) and muxes the source audio, applying
    the `atempo` drift correction and `adelay` offset at this point rather than
    during video encoding. The audio mapping is optional (`1:a:0?`), so a
    video-only source still finalizes instead of failing the whole job.
  - `_build_ffmpeg_cmd()` is now the video-only segment command and
    `_build_mux_cmd()` is the new join-and-mux command; audio arguments moved
    with the audio.
  - The result is written inside the workspace and then renamed onto the final
    output path, preserving the existing atomic-rename guarantee.

- **Long tapes (4 h and beyond)**:

  - Segmentation is what makes long captures practical: a 4 h PAL tape is
    720,000 output frames and 48 five-minute segments, each a separate
    vspipe/FFmpeg process, so memory is released between segments and a power
    cut costs at most one segment. The segment index is four digits, which
    covers more than 800 hours at the default length.
  - The `vspipe --info` probe builds the source index on its first run, and
    indexing time grows with the file, so its hang guard now scales with the
    source: 30 minutes plus 5 minutes per gigabyte (`resolve_info_timeout()`),
    instead of a fixed cap that a long tape on a slow drive could exceed. A
    timeout there would abort the index build, which cannot resume, and silently
    fall back to a single unchunked segment.
  - Disk space is the other constraint at this length: a 4 h ProRes HQ tape is
    roughly 260 GB of output, and during the join the finished segments and the
    muxed part file coexist, so the peak is about twice that. After the first
    segment encoded in a run the pipeline projects the final size and the peak
    from that segment's bytes-per-frame and logs them against the free space on
    the workspace drive (`[SPACE] Projected output ~262 GB; peak during the join ~524 GB; free ...`), with a warning when free space is below the peak.
  - Immediately before the join the check is exact: the join is refused when
    the drive cannot hold a copy of the segments plus a margin. The segments are
    kept, so freeing space and re-running the same file continues straight at
    the join rather than re-encoding anything.
  - When resume is impossible, because the frame count could not be probed or
    `resume_segment_minutes` is `0`, the plan says so as an error line instead
    of silently running the whole tape as one segment.

- **Progress reporting across segments**:

  - `_run_encoding_pipeline()` takes an `offset_sec` for the segment start, so
    the percentage, timestamp and ETA stay whole-file and never restart per
    segment. The displayed position is clamped to the total duration.

- **Temp-file leaks closed**:

  - `<stem>_temp_script.vpy` beside the source → `restore.vpy` in the workspace.
  - `<output>_part.<ext>` beside the final output, never cleaned on failure →
    inside the workspace, removed with it.
  - FFMS2 index in `%TEMP%/auto-vhs-deinterlancer/ffms2/*.ffindex`, never
    removed → `index/source.ffindex` in the workspace. L-SMASH (`.lwi`) and
    BestSource caches are redirected to the same folder. There is no fallback
    that drops the cache argument: that would put the index back beside the
    source, so a genuine source or index failure propagates unchanged and only a
    plugin build that rejects the cache argument itself is reported, as an
    explicit compatibility error.
  - `cleanup_temp_files()` used to glob `*.vpy` across the source folder and
    delete any file whose name merely contained `temp`, which could remove a
    user's own files. It now matches only artifacts derived from the input stem
    (`_temp_script.vpy`, `_intermediate.*`, `.ffindex`, `.lwi`, `_part.*`) and
    exists purely to sweep leftovers from earlier versions.
  - `cleanup_legacy_cache_dir()` removes the pre-1.1.3 system-temp index cache
    once during pre-flight.
  - Three tests wrote `.vpy` files into the repository root on every run
    (`test_temp_script.vpy`, `trim_test_temp_script.vpy`). The unit and
    integration suites now run from a temporary working directory via new
    `conftest.py` fixtures, so a test cannot leak into the checkout.

- **Native fallback frame ranges** (`modules/runtime/vspipe_native.py`):

  - The Python fallback writer accepts `--start N` / `--end M` with vspipe's
    inclusive-end semantics, so it can serve the same segment plan as the real
    `vspipe` binary.

- **Supporting changes**:

  - Input discovery (CLI arguments, folder scan, interactive prompt) moved from
    `pipeline.py` into a new `modules/runtime/inputs.py`, and encoder argument
    selection into a new `modules/runtime/encoders.py`. `pipeline.py` grew a
    whole encoding stage, and the splits keep it at Radon maintainability
    grade A and under the 1000-line module limit without loosening either
    policy.
  - Folder scans no longer re-queue finished outputs when `output_suffix` or
    `output_suffix_av1` is customised: the configured suffixes are excluded
    from input discovery alongside the historic `_deinterlaced` and
    `_intermediate` markers. Previously a custom suffix such as `_restored`
    let a scan pick up `tape_restored.mov` and deinterlace it a second time.
  - The native `vspipe` fallback rejects negative or inverted `--start` /
    `--end` ranges the way `vspipe` does. Under Python slicing a negative bound
    silently counted from the end of the clip and `end < start` silently
    produced an empty clip; both would have corrupted a segment rather than
    failing the job.
  - The `vspipe --info` timeout was raised from 30 s to 1800 s
    (`VSPIPE_INFO_TIMEOUT_SEC`). The probe builds the source index on first run,
    which takes minutes on a long capture and previously aborted the job.
  - `.gitignore` ignores `*.autovhs-tmp/`.
  - The coverage-summary step could never complete on Windows: the report
    contains non-ASCII characters, and both the Python side (a redirected stdout
    defaulting to cp1252) and the PowerShell side (decoding the captured output
    with the OEM code page) mangled or rejected them. The script now forces
    UTF-8 on stdout and `run_pipeline_localy.ps1` sets
    `[Console]::OutputEncoding` while it captures, so the local pipeline
    finishes and writes an uncorrupted `assets/coverage_summary.md`.
  - `install.sh` on Fedora was broken in three places, found by the new
    Fedora container harness (see Validation): the source-build fallback lacked
    `zlib-devel` (`zlib.h` missing during the ffms2 build); the copy of the
    system `libffms2` only looked in `/usr/lib` and `/usr/lib/*` and never in
    Fedora's `/usr/lib64`; and even when found, Fedora's own ffms2 is linked
    against `libavcodec-free`, which carries no H.264 decoder, so opening the
    most common capture format failed with "decoder returned an empty frame".
    The installer now enables the RPM Fusion free repository and installs its
    full `ffmpeg-libs` together with `ffms2` (asking for `ffmpeg-libs`
    explicitly matters: `dnf install ffms2` alone is satisfied by the `-free`
    libraries), which was verified to expose the `h264`, `mpeg2video` and
    `mpeg4` decoders.
  - `.dockerignore` anchors its cache patterns with `**/`: a bare
    `__pycache__/` only matches the repository root in Docker's ignore syntax,
    so bytecode compiled on the Windows host under `modules/` and `tests/` was
    being copied into the Linux images.

- **Tests**:

  - New `tests/unit/test_workspace.py` covers the workspace layout, partial-file
    removal, atomic and corrupt state handling, fingerprint sensitivity, the
    segment plan and concat-list escaping. `modules/runtime/workspace.py` is at
    100% line and branch coverage.
  - New `tests/integration/test_pipeline_resume.py` drives `process_video()`
    against real files in a temp folder with only the external boundaries
    (vspipe/FFmpeg processes, `ffprobe` durations) mocked. It asserts that a
    successful run leaves only the source and the output, that no temp file ever
    appears outside the workspace during encoding, that an interrupted run keeps
    exactly the finished segments, that the rerun resumes from the last one,
    that a stale `.part` file is discarded, that changed settings invalidate old
    segments, and that a failed mux keeps the workspace for resume.
  - The drift-correction tests were retargeted from the old single-pass FFmpeg
    command to the two seams that now carry the decision,
    `_calculate_audio_sync()` and `_build_mux_cmd()`.
  - New coverage for the native frame-range parsing and slicing, the narrowed
    legacy cleanup, the legacy cache-directory removal, and
    `resume_segment_minutes` validation.
  - The suite no longer skips work it can actually do on Windows. The
    `install.sh` shell tests used to skip on every Windows host on the
    assumption that `bash` there is the WSL launcher; they now locate a real
    POSIX bash (Git Bash) and translate the paths they embed into shell strings,
    so all seven run locally. The two CPU-name fallback tests were split by
    platform even though both are fully mocked; they now run everywhere. Only
    the `install.sh` end-to-end installer test still skips on Windows, because
    `install.ps1` is the Windows install path and has its own tests, and that
    scenario runs on the Linux and macOS CI jobs.
  - Those `install.sh` FFmpeg tests then failed on the GitHub Windows runner
    while passing on every developer machine. The runner puts `Git\bin` first
    on PATH, and that `bash.exe` is a wrapper which prepends Git's own bin
    directories before starting the real MSYS2 bash, so the `curl` stub the
    tests prepended to PATH was shadowed by the real curl, which downloaded the
    real archives from evermeet.cx. The stub is now a shell function defined in
    the driver script, which shadows curl under any PATH, and the tests prefer
    the MSYS2 bash under `Git\usr\bin` over whatever is first on PATH.
  - The Windows Real-Dependency E2E CI job had never run a real-dependency
    scenario: it set `AVD_SKIP_FFMPEG=1`, copied from the macOS job where
    Homebrew provides FFmpeg first, but the Windows runner image ships no
    FFmpeg at all, so every scenario skipped on the missing binary (on `main`
    the job reported 16 skips). The job now lets `install.ps1` bundle the
    gyan.dev FFmpeg the way a user install does, with AV1 going through the
    runtime encoder probe, and pytest runs with `-rs` so the reason for any
    skip is in the CI log.

- **Documentation**:

  - `README.md`, `docs/pipeline_logic.md`, `.agent/architecture.md` and
    `AGENTS.md` describe the workspace layout, the segmented execution model,
    the resume behaviour and the two new runtime modules.

## Fixed: AV1 CPU fallback on Windows

The AV1 CPU path hard-coded `libsvtav1`, but `install.ps1` installs the
gyan.dev **essentials** FFmpeg build (`ffmpeg-9.0.1-essentials_build.zip`),
which is compiled with libaom but **not** SVT-AV1. Every AV1 encode that could
not use NVENC therefore died with `Unknown encoder 'libsvtav1'` on a default
Windows install. The bug predates this release: the same failure reproduces at
tag `v1.1.2` against the same FFmpeg.

`get_av1_cpu_encoder_args()` in the new `modules/runtime/encoders.py` now asks
the active FFmpeg which encoders it has
(`get_available_ffmpeg_encoders()`, a cached `ffmpeg -encoders` probe) and picks
the first available option in preference order: `libsvtav1`, then `libaom-av1`
with the `-b:v 0` that libaom needs for constant-quality mode. If the listing
cannot be read the SVT arguments are kept unchanged, so FFmpeg still reports the
missing encoder itself rather than the pipeline guessing. The selected encoder
appears in the `[ENCODER]` log line and, because the resolved arguments are part
of the resume fingerprint, switching encoders correctly invalidates existing
segments.
