# v1.1.4

## Summary

v1.1.4 closes a supply-chain gap in the Linux installer and brings the bundled
FFmpeg to 9.0.2 on every platform.

Before this release, `install.sh` on Linux downloaded FFmpeg from the moving
`latest` release of BtbN/FFmpeg-Builds and verified the archive against a
`checksums.sha256` fetched from that same release. The check only proved that
the two files agreed with each other: anyone able to replace the release could
swap the archive and the checksum file together and the installer would accept
it, then copy the binaries into `.venv/bin/`, where the app puts them first on
`PATH` and runs them against every video. Windows (`install.ps1`) and macOS
(`install_darwin_ffmpeg`) already pinned their expected SHA-256 in the installer
itself; Linux did not.

All three platforms now pin both the exact FFmpeg release and its SHA-256 in the
installer, refuse to install anything that does not match, and only skip the
download when the binaries already in `.venv` report that exact version — so
upgrading the pin actually replaces what a previous install left behind.

## Highlights

- **Linux FFmpeg is pinned and verified against a hash in the installer**
  (`install.sh`, new `install_linux_ffmpeg`):

  - Downloads from the fixed BtbN release tag `autobuild-2026-09-19-13-11`,
    the clean `n9.0.2` build, instead of `latest`.
  - The SHA-256 of the `linux64` and `linuxarm64` archives is pinned in the
    script, the same pattern `install_darwin_ffmpeg` and `install.ps1` already
    use. The `checksums.sha256` download is gone entirely, since a checksum
    file hosted in the same release as the archive proves nothing.
  - A mismatching archive is deleted and the download retried up to three
    times; after that nothing is installed and the pipeline falls back to the
    system FFmpeg with a warning.
  - The block is now a self-contained function, `install_linux_ffmpeg <tmp_dir>
    <uname -m>`, so the unit tests can execute it against fixture archives with
    a stubbed `curl`, exactly as they already did for the macOS function.
  - The unused `FFMPEG_SERIES` constant is removed; `FFMPEG_VERSION` is the one
    place the exact release lives.

- **Bundled FFmpeg 9.0.1 → 9.0.2 on all platforms**:

  - macOS: evermeet.cx `ffmpeg-9.0.2.zip` / `ffprobe-9.0.2.zip`, pinned hashes
    refreshed.
  - Windows: gyan.dev `ffmpeg-9.0.2-essentials_build.zip`, pinned hash
    refreshed.
  - Linux: BtbN `ffmpeg-n9.0.2-<arch>-gpl-9.0.tar.xz` as above.
  - Every hash was computed from an independently downloaded archive and
    cross-checked against the upstream-published value where one exists
    (gyan.dev's `.sha256`, BtbN's `checksums.sha256` for the pinned tag).
    evermeet publishes no checksum file, so those two values are computed
    only, the same situation as the previous 9.0.1 pins.

- **The installer only skips the download for the exact pinned version**:

  - `install.sh`: `ffmpeg_is_90`, which accepted any 9.0.x, is replaced by
    `ffmpeg_is_pinned`, which requires both `ffmpeg` and `ffprobe` in `.venv`
    to report exactly `FFMPEG_VERSION`. The matcher accepts evermeet's
    `version 9.0.2`, BtbN's `version n9.0.2-20260919` and gyan's
    `version 9.0.2-essentials_build…` while rejecting `9.0.1` and `9.0.21`.
  - `install.ps1`: the `Test-Path ffmpeg.exe` existence check is replaced by
    `Test-FfmpegPinned`, which probes `ffmpeg.exe -version` and
    `ffprobe.exe -version` with the same rule.
  - Net effect: a machine that installed 9.0.1 under v1.1.3 gets 9.0.2 on the
    next `./install.sh` / `.\install.ps1`, rather than silently keeping the old
    bundle.

- **No stale bundle after a failed upgrade**:

  - `install.ps1` now removes any existing `ffmpeg.exe` / `ffprobe.exe` from
    `.venv\Scripts` when the download, hash check or extraction fails, so the
    app falls back to the system FFmpeg instead of running the previous bundle
    that `setup_environment()` would otherwise put first on `PATH`.
    `install.sh` already did this.
  - In both `install_linux_ffmpeg` and `install_darwin_ffmpeg`, the final
    `cp` + `chmod` run as one conditional. A disk-full or permission error no
    longer aborts the installer under `set -euo pipefail`; `FF_OK` stays `0`, a
    warning is printed, and the caller removes any partial copy.

- **Linux installer path is now covered by tests**
  (`tests/unit/test_runtime_helpers.py`):

  - `test_install_sh_verifies_download_hashes` asserts both Linux pins, the
    exact release tag, and that `install_linux_ffmpeg` never references
    `releases/download/latest` or `checksums.sha256`.
  - `test_install_linux_ffmpeg_accepts_matching_archive` (parametrised over
    `linux64` and `linuxarm64`) serves an archive laid out like the real BtbN
    build for that architecture and checks that exactly one download was made,
    from the pinned tag, and that both binaries are installed executable.
  - `test_install_linux_ffmpeg_rejects_digest_mismatch` serves a tampered
    archive and checks it is rejected and deleted on all three attempts, with
    nothing installed and nothing extracted.
  - `test_install_linux_ffmpeg_handles_download_failure` and
    `test_install_linux_ffmpeg_skips_unsupported_arch` cover the remaining
    branches.
  - The macOS fixtures are updated to the 9.0.2 file names and hashes.

- **Ubuntu E2E image no longer depends on Launchpad**
  (`docker/Dockerfile.ubuntu`):

  - The image installed Python 3.12 from the deadsnakes PPA, so every CI run
    depended on `ppa.launchpadcontent.net`. During this release Launchpad
    returned HTTP 500/503 for over an hour and the required Docker E2E check
    failed four times before any project code ran.
  - Python 3.12 now comes from uv's managed builds (python-build-standalone,
    fetched from GitHub and SHA-256-verified by uv), with uv 0.12.17 copied
    from GHCR pinned by tag and digest. It is exposed as `python3.12` on
    `PATH`, so `install.sh` and the rest of the image are unchanged.
  - `tests/e2e/test_dockurr_containers.py` asserts the image never references
    `add-apt-repository` or the PPA and that uv is pinned by digest.

## Validation

- The full local pipeline (`./run_pipeline_localy.sh`) passes end to end:
  Taplo, Bandit, pip-audit, Black, isort, Ruff, Flake8, Pylint (10.00/10),
  Radon complexity and maintainability (all grade A), Markdown lint, the test
  suite and both coverage gates. The 2026-09-21 release run: 373 tests passed,
  0 skipped, 0 failed; 95.51% line coverage and 87.18% branch coverage, with
  the gate and badge at 93.68% (the combined line-plus-branch figure). Every
  product file is above the 90% per-file line threshold.
- The rewritten installer paths were exercised for real, not only with stubs:
  - `install_linux_ffmpeg` against the live BtbN release installs
    `ffmpeg version n9.0.2-20260919`; with a stubbed `curl` returning tampered
    bytes it warns three times, deletes the archive each time and installs
    nothing.
  - `install_darwin_ffmpeg` against the live evermeet.cx 9.0.2 archives passes
    the new pins and stages both binaries.
  - With a fake 9.0.1 pair in `.venv/bin`, the skip check downloads and
    replaces them; a second run reports `Local FFmpeg 9.0.2 already present`.
  - With a read-only `.venv/bin` under `set -euo pipefail`, staging fails with
    a warning, the script reaches the end with `FF_OK=0` and exits `0`.
  - `install.ps1` parses cleanly under `pwsh`, and `Test-FfmpegPinned` was
    checked against the five version-string shapes above. The Windows
    installer was not executed end to end on a Windows host for this release;
    the Windows real-dependency E2E job in CI covers that.
- The new tests were confirmed to catch regressions: removing the
  delete-on-mismatch guard, changing the pinned tag, or hard-coding the
  `linux64` directory name in extraction each fails at least one of them.

## Known issue (pre-existing, unchanged)

- `poetry lock` cannot re-resolve from scratch on the current `pyproject.toml`:
  `nvidia-cuda-runtime 13.2.86` conflicts with the `==13.2.75.*` pin that
  `torch 2.14.0+cu132` carries. The committed `poetry.lock` is consistent
  (`poetry check --lock` passes) and the pipeline uses it as is, so this does
  not affect installs or CI; it only matters when a dependency is next
  changed. This predates v1.1.4.
