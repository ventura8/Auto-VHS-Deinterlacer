# v1.1.6

## Summary

v1.1.6 fixes the four issues SonarQube Cloud reported on `main` after v1.1.5,
bringing the project back to zero open issues. Three were vulnerabilities in the
Radon quality gate script: the gate passed command-line arguments to `radon` and
to its summary writer without checking them. The fourth was a shell code smell
in the macOS package builder. Product code (`auto_deinterlancer.py` and
`modules/`) is unchanged.

The Radon gate fix combines two independent fixes: pull request #10 and the
v1.1.6 release branch. It keeps the stronger check from each.

## Highlights

### The Radon gate only accepts paths inside the working tree

- SonarQube flagged `.github/scripts/enforce_radon_grade.py` three times: two
  command argument injections (`pythonsecurity:S8705`, in `run_radon` and
  `run_radon_mi`) and a path traversal (`pythonsecurity:S8707`, in
  `_write_summary`). In each case a command-line value reached a subprocess or
  a file write unchecked.
- `_confine_to_working_tree` resolves every target and the `--summary-out` path
  against the working directory. That is the repository root in CI and in both
  local pipelines. A path that escapes it, through `..`, an absolute path
  elsewhere, or a symlink, stops the run with exit status 2 before `radon`
  runs or anything is written.
- A target that looks like an option (`-x`, `--output-file=x`) is also refused
  with status 2. As a second guard, both `radon` commands pass `--` before the
  targets.
- Accepted targets reach `radon` as working-tree-relative POSIX paths.
  Equivalent spellings such as `./modules/../modules`, or an absolute path
  inside the tree, therefore analyse and report the same way. The default runs
  are unchanged, and both gates still pass at grade A.
- `tests/unit/test_enforce_radon_grade.py` (new, 17 tests) covers:
  - accepting and refusing summary paths and targets;
  - normalising targets to relative paths;
  - the option guard;
  - the `--` in both commands;
  - the status-2 exits.

### macOS package builder

- `tools/packaging/macos/build_pkg.sh` now uses `[[ ... ]]` for the
  architecture test SonarQube reported (`shelldre:S7688`). The same change is
  applied to the embedded `.app` launcher's virtual-environment check.

### Documentation

- The `code-linter` skill describes how the Radon gate handles paths outside
  the tree and option-like targets.
- Version 1.1.5 -> 1.1.6 in `pyproject.toml`, `sonar-project.properties` and
  `AGENTS.md`.

## Known issues

- Unchanged from v1.1.4: `poetry lock` cannot re-resolve from scratch, because
  `nvidia-cuda-runtime 13.2.86` conflicts with the `==13.2.75.*` that
  `torch 2.14.0+cu132` requires. The committed lock is consistent
  (`poetry check --lock` passes), so installs and CI are unaffected.
- Found during this release, not caused by it: the Bash-driven installer tests
  call Git's `usr\bin\bash.exe` directly. That MSYS bash only finds `head`, `rm`
  and `basename` when `C:\Program Files\Git\usr\bin` is already on `PATH`.
  From a PowerShell session without that entry, 12 tests fail with
  `command not found`. They pass from Git Bash, on GitHub's runners, and once
  that directory is on `PATH`.
- The Radon gate checks the summary path before writing. It does not guard
  against another process swapping a directory for a symlink between the check
  and the write. The gate runs in CI and local checkouts, and only ever writes
  under `assets/`.
